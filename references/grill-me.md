
# Grill-me：把模糊愿望问成可执行决定

目标是理解用户真正想做什么，以及愿意为此舍弃什么。详细体现在追问的深度、矛盾的消解与可验收的决定，不能用题数代替。先读已有上下文，再问最能改变结果的未知项。

## 开始方式

1. 读取请求、已有决定与相关项目资料；已有仓库时检查代表页面、组件、资产、运行说明。能从文件或工具查明的事实自己查。
2. 分清本次是探索想法、完整重设计、已有系统内扩展，还是局部打磨。不要把局部改色升级为产品战略访谈。
3. 对明显模糊的完整设计任务，默认深入访谈。用户要求快做、已经给全 brief 或已授权自主判断时，只问影响方向且无法推断的关键项；可逆细节用具名假设推进。
4. 设计任务按需读取 [references/question-bank.md](question-bank.md)。一般计划沿用下述方法，题库只取适用分支。

## 决策树与追问

建立一个小型决定表：`ID | 问题 | 前置决定 | 状态 | 答案/依据 | 影响`。
状态使用「已知事实 / 用户决定 / agent 建议 / 待回答 / 暂定假设 / 不适用」。这些状态不能混写；已查到、已回答的内容不再问。

按依赖推进：目标和用户 → 核心任务与成功标准 → 范围与约束 → 信息架构和状态 → 视觉表达 → 验收。
例如核心任务尚未明确时，不先问卡片阴影；未确定信息密度时，不让用户选择字号。

每轮默认问一个最高影响的问题；用户偏好集中回答时，可把 2–3 个互不依赖的问题合并。前一题的不同答案会改变后一题选项时，拆到下一轮。不要一口气倾倒整个题库。

每个问题包含：

- **具体选择**：放进用户的真实场景，避免「想要高级还是简洁」这种无法行动的形容词投票。
- **为什么现在问**：一句话说明它会改变哪个页面、流程或验收结果。
- **2–3 个可比较选项**：列出收益与代价，给有依据的推荐，允许用户自由补充。信息不足时用开放题，不捏造选项。
- **等待真实回答**：未回答的依赖继续待定；没有回复、工具超时或默认预选都不算同意。

优先使用宿主实际提供的结构化提问工具，如 AskUserQuestion 或 request_user_input。遵守工具可用模式和选项数量；工具不可用时，直接用普通对话提出同样的问题。不要因工具名称不同停住，也不要伪造调用。

拿到回答后，用一句话复述它对设计的影响，再更新决定表。只对真正重要的回答继续追一层：

- **具体化**：「专业」具体指信息能一眼比较，还是视觉更克制？
- **情境化**：请给最近一次真实使用场景；第一次进来和每天使用是否不同？
- **取舍**：若只能保住一个，先看全貌还是先处理一条异常？
- **反例**：做成什么样，即使精致也会让你拒绝？
- **压力测试**：数据为空、记录很多、断网或长标题时，这个决定还成立吗？
- **验收**：做完后凭什么判断比现在好？使用任务结果或可观察行为，不编造提升比例。

不要对每个答案机械追六遍。优先处理相互矛盾的要求，例如「高密度」同时要求「每行放巨大卡片」。展示冲突及两种可行取舍，让用户决定目标；由 agent 负责技术数值和实现细节。

## 审美问题怎么问

先确定要让哪类用户在什么场景感受到什么，再把词翻译成可见差异。
例如「安静但有识别度」可对应：低噪声列表、清晰字重对比、只在品牌区使用一种强调色；不能直接等同于米白底、衬线体或玻璃。

用户说「都行」「你来定」时，提出一个推荐与代价，按授权记录为 agent 决定并继续。用户说「更高级」时，先定位最不满意的维度；如果文字仍无法区分，用相同真实内容的两个代表性片段比较，让用户看层级、密度、材质和排版的实际差别。

已明确的品牌、参考继承范围和否定项优先于 agent 的个人偏好。不要强迫用户选择行业通用的风格标签，也不要把参考品牌整体搬过来。

## 为技术路由留下可执行输入

涉及动效或空间体验时，在体验方向明确后补齐：最终交付是可操作网页还是成片；谁触发、能否拖动/中断/旋转；哪些文字数据必须准确；目标设备、资产和失败退路。能从项目查到的框架/库版本自己查。

用户补充的设计想法作为独立决定记录，不能被参考 skill 覆盖。先问“自由旋转还是固定镜头播放”，再由 agent 选择 Three.js 或视频等方案；不要求用户替 agent 选库。清楚的已有约束直接传递，避免新增确认轮。

涉及动画文件/模型/字体等资产时，确认可得状态和制作条件；涉及图表时先问要回答的问题与数据来源。只补会改变方案的未知项。将这些输入与决定 ID 一起交给 design-flow 的技术路由。独立使用 grill-me 时仍只交接决定，不要求安装设计流程或任何动效工具。

## 停止条件与交接

核心目标、主要用户任务、改动范围、不可改项和成功标准都有依据，且没有会改变方案的关键待回答项时结束。明确 brief 可零新增问题；深入探索可以多轮，不设置最低题数或强制轮数。

独立访谈任务到决定摘要结束。访谈嵌入实现任务时，按用户既有授权继续下一阶段，不重复索要开工许可。纯访谈不隐含实施或发布授权。

在项目已有 DESIGN.md 的相关章节追加或合并以下内容，不覆盖其他人的决定；无文件写权限时在对话交接：

```markdown
## 访谈定案
- 目标/用户/场景：
- 核心任务与成功标准：
- 范围、优先级、不可改项：
- 已决定的体验与视觉取舍（含理由与回答来源）：
- 暂定假设（谁提出、影响、何时验证）：
- 未解决问题（只保留实际未解决项）：
- 下一步和需要复看的页面/状态：
```

其他 agent 接手时先读这些决定，只问新增或已失效的问题。不要把 agent 推荐、用户尚未选择的方案写成「用户已确认」。
